# Boondock Echo — Feature Inventory (Legacy vs Current)

This document summarizes **high-level features** of the Boondock Echo firmware, comparing:

- **Current**: `Release-2026-03-25` branch (this workspace)
- **Legacy**: `LEGACY-ECHO-2024` branch

It is intentionally **feature-focused** (behavior/capabilities) and avoids code-level details.

---

## Current firmware (Release-2026-03-25): what it does today

### Audio capture (core function)
- **Continuous audio monitoring + threshold-triggered recording**
  - dB-based threshold with smoothing and a configurable sensitivity mapping.
- **Pre-record buffer**
  - Captures a short “lookback” window so recordings include audio just before the trigger.
- **Recording lifecycle + metadata**
  - Tracks per-recording stats (duration, peak dB) and per-session stats (record count, upload count, error count).
- **WAV recordings**
  - Recordings are stored as `.wav` (and served as `audio/wav` via HTTP).

### Storage model (SD-first with resilient fallbacks)
- **SD card recording mode**
  - Uses filesystem layout as the queue: `/pending/YYYY/MM/DD/...` then moved to `/inbox/...` on success.
- **PSRAM fallback recording**
  - If SD is unavailable, records into PSRAM buffers and queues a limited number of recordings for upload.
- **Hybrid SD “memory queue”**
  - Prioritizes recent SD recordings via a lightweight in-memory basename queue (avoids expensive full scans).
- **Trash handling**
  - Supports moving `.tmp` artifacts to `/trash/...` to keep queues clean.

### Upload + cloud connectivity
- **Multi-endpoint upload**
  - Multiple API endpoints (regions + optional custom), per-endpoint enable flags.
- **Queue-driven upload task**
  - Prioritizes in-memory/PSRAM queues, then falls back to filesystem scanning for orphaned `/pending` items.
- **Network health tracking**
  - Tracks RSSI, endpoint success/failure, response times, and “cloud path” TCP health (STA can be up while API is unreachable).
- **Settings push/pull to server**
  - Supports pushing and pulling the device settings JSON to/from the API (synchronization feature).
- **Offline mode (local-only)**
  - When enabled and SD is present: no cloud upload/events; runs local AP for UI.

### Web UI + API (device-hosted)
- **Access Point mode for configuration**
  - Boots into AP mode when offline/no WiFi credentials, exposing configuration UI.
- **Main web UI (SPA)**
  - Embedded HTML/CSS/JS served from firmware (not from SD file packs).
- **HTTP API endpoints** (representative)
  - **Device info** (`/api/device-info`)
  - **Time sync (UTC from browser, offline use-case)** (`/api/time/sync-utc`)
  - **Audio stats + audio settings** (`/api/audio/stats`, `/api/audio/settings`, defaults/save)
  - **Recordings browsing** (`/api/recordings/folders`, `/api/recordings/list`, `/api/recordings/summary`)
  - **Recording streaming to browser** (`/api/recordings/stream?path=...`)
  - **Unified command endpoint** (`/api/cmd`) for batch get/set (aligned with CLI parameter model)
  - **Firmware check/apply + update upload** (`/api/firmware/check`, `/api/firmware/apply`, `/api/advanced/update-firmware`)
  - **Admin operations** (reboot, set-default, factory-reset, export/import settings, push/pull settings)

### Live audio streaming (to browser)
- **Live audio buffer + WebSocket delivery**
  - Maintains a circular buffer (PSRAM-backed) and pushes live audio to connected clients.
- **VU-meter / audio telemetry to UI**
  - Periodic audio stats for visualization and monitoring.

### Timekeeping
- **RTC support (configurable)**
  - RTC enable flag, pin configuration, and chip selection (auto/DS3231/MCP79410).
- **Timezone + maintenance window**
  - Timezone offset and configured daily maintenance time.

### Logging, diagnostics, and safety
- **Structured JSON logs and periodic health/config messages over Serial**
  - Designed for tooling ingestion and UI display.
- **Log filtering**
  - Separate log-level enablement for Serial vs file.
- **Memory safety monitoring**
  - Heap integrity checks and safety reboot thresholds.
- **Task health metrics**
  - Tracks task stack health and restart metrics (where applicable).

## Legacy firmware (LEGACY-ECHO-2024): notable capabilities

### On-device audio UX (speaker prompts)
- **On-device alert playback**
  - Plays boot warnings and mode announcements using local WAV assets when present.
- **Beep patterns**
  - Uses tones as fallback when WAV assets are missing.
- **Spoken/system prompt library**
  - Included a large `system/` audio asset set (letters, numbers, months, prompts).

### Radio interaction & control
- **PTT input + PTT output keying**
  - Hardware PTT input, plus a PTT output GPIO for keying transmit.
- **Audio transmit path**
  - Ability to transmit audio (and potentially play-or-transmit flows).
- **Repeater modes**
  - **Simplex** and **duplex** repeater modes as explicit device startup modes.

### Hardware button-driven startup modes
- Boot-time key combos for:
  - **WiFi configure**
  - **Offline**
  - **Simplex repeater**
  - **Duplex repeater**
  - (and other “function” activations)

### MQTT-based integration
- **MQTT client + topic command handling**
  - Connect, periodic “online” ticker, audio-level ticker, and message-based commands.

### CDN-style asset/content management
- **Download/update “system / essential / web” file packs**
  - Pulled lists and assets from a CDN onto local storage.

### Licensing & registration hooks
- **License validation function surface**
  - License code validation and “license code playback” behaviors were present in the legacy API surface.
- **Registration workflows**
  - Legacy included registration/linking checks and related boot warnings.

## Features present in Legacy that are **missing** (or not implemented) in Current

### Device-local audio playback (speaker output)
- **Missing**: On-device playback of alerts/messages (legacy `playAlert`, `playMessage`, spoken boot/mode prompts).
- **Current replacement**: Browser playback via `/api/recordings/stream` (HTTP streaming) + web UI status.

### Transmit / PTT / repeater behavior
- **Missing**: Audio transmit path and PTT keying control as a first-class device feature.
- **Missing**: Simplex/duplex repeater modes and the mode-selection model.
- **Missing**: Boot-time hardware key combos that activate those modes.

### MQTT command/control plane
- **Missing**: MQTT connect + subscriptions + topic command processing + periodic MQTT tickers.

### System WAV prompt pack + spoken diagnostics
- **Missing**: Bundled `system/` WAV asset library and the firmware logic that relies on it for spoken prompts.

### CDN file-pack downloader model
- **Missing**: “download system/essential/web files” model used to refresh assets from a CDN onto storage.
- **Current approach**: Embedded SPA assets in firmware image instead of SD-hosted web files.

### Legacy licensing workflow surface
- **Missing**: Legacy “license code” validation/playback user experience (as implemented in 2024-era Echo).

## Features that look “similar” but are **implemented differently now**

### Playback
- **Legacy**: playback on the device (speaker), including prompts and messages.
- **Current**: playback/streaming to a **browser client** via `/api/recordings/stream` and live audio over WebSocket.

### Offline mode
- **Legacy**: multiple offline/repeater-specific modes (offline, simplex, duplex) driven by key combos and config fields.
- **Current**: a single **offlineMode** concept (local UI, no cloud upload/events) that depends on SD being enabled.

### Eventing/telemetry
- **Legacy**: MQTT-based tickers + serial command processing.
- **Current**: HTTP API + WebSocket push + structured JSON over Serial; cloud events via `sendEvent(...)`.

## Practical “Echo roadmap” checklist (if you want parity)

If the goal is to bring Echo back toward legacy device behavior, the biggest parity gaps are:

- **On-device speaker playback** (alerts, prompts, message playback)
- **PTT keying + transmit audio path**
- **Simplex/duplex repeater modes + mode selection**
- **MQTT control plane** (if still desired)
- **System prompt asset strategy** (reintroduce `system/` pack or a new embedded prompt mechanism)
